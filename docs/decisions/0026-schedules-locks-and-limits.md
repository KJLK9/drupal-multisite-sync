# 26. Schedules, a lock on the wizard, limits on a source, and cleaning up

Date: 2026-10-12 · Status: accepted · Qualifies ADR 0009, 0012 and 0015

## Context
After the review of 12 October, and a list from the person who runs the engine: imports must run by themselves but never more often than every quarter of an hour, two people must not overwrite each other in the wizard, a source must not be able to hurt the engine with a huge answer or by being called when it asked to be left alone, and what the engine kept for an import that was deleted must go. Also asked, and decided against for now: partitioning the tables.

## Decision
- **A schedule is a property of an import and of a run set**: every so many minutes, from a time of day, in whole quarters of an hour and UTC. The periods that can be chosen are those that divide a day (15, 30, 60, 120, 180, 240, 360, 480, 720, 1440 minutes), so that every day looks the same. One job asks every 15 minutes what is due (`drush import:run-due`); the engine keeps no clock. A quarter is started once (the last slot is remembered per target), a run that is not over is continued, and an import that is in a run set that is due is left to the set. A quarter that no call falls in is not made up for. The alternatives were a cron expression (more than the person who runs it wants, and easy to make finer than the job that calls it) and one Kubernetes CronJob per import (a lot of objects that have to follow the configuration).
- **One person at a time edits an import in the wizard.** The wizard keeps the whole import in the form and saves it at the end, so two people overwrite each other without knowing. Opening an import takes a lock (15 minutes, renewed at every step, released on save); a second person is told who has it and may take it over; the one who lost it is told at the next step and nothing of theirs is saved over the other's work. The same person in two tabs is not locked out. A new import has no lock. The lock is in the expirable key-value store, so it needs no table, and it fails open (a lost lock means nobody is blocked) rather than shut.
- **A response is read up to a limit** (20 MB after decompression, `import_engine_max_response_bytes` in `settings.php`), with `Content-Length` checked first: a larger answer is a permanent error that says what to do. **`Retry-After`** (seconds or a date, at most an hour) opens the circuit breaker for that time at once, instead of counting failures until the threshold: the server said how long to wait.
- **Deleting an import deletes what the engine kept for it**: its runs, queue, events, pages and the mapping of source items to entities. It does not delete the entities it wrote. A new import with the same name must not start from the mapping of the old one. This happens in a hook, so it is the same in the interface, with drush and in a configuration import.
- **Partitioning the tables is not built.** The item table is a work queue that is purged after 7 days; the events table (`id`, `occurred`) could be partitioned by month by someone who administers the database, and the key is made for it. Built-in partition maintenance (creating and dropping partitions by cron) was considered and left out: MySQL and MariaDB do not create or drop partitions by themselves, so it would be one more thing for the engine to run and to keep working, for a table that the row-by-row purge handles at the sizes tested.

## Consequences
- A run set's schedule and its imports' schedules can both be set; when both are due, the set wins.
- A schedule does not run when the job that asks is not running; the job (a CronJob) is part of what has to be monitored.
- The lock is advisory in the interface only: the configuration can still be changed by `cim` or drush while someone has the wizard open, and the wizard then overwrites it on save.
