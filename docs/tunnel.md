# Reaching the sites from the internet, from this machine

The sites run in a k3d cluster on a development machine
([deploy.md](deploy.md)). A **Cloudflare Tunnel** makes them reachable from
outside without opening anything: a small program in the cluster (`cloudflared`)
connects *outward* to Cloudflare, and Cloudflare sends visitors' requests back
through that connection. The router stays closed and the home address stays
hidden. The machine has to be on, and online, while people look.

**Status: tried.** The sites have run through a tunnel, with Cloudflare Access
in front. Things learned on the way are in the text: the one-level hostnames
and the One-time PIN login method.

## What you need

- A **domain** on Cloudflare (the free plan is enough). Buy one there, or buy
  elsewhere and point its name servers to Cloudflare. The sites are
  `site-a-import-engine.<domain>` and `site-b-import-engine.<domain>`. Use
  **one level** below the domain: the free certificate of Cloudflare covers
  `<domain>` and `*.<domain>` and nothing deeper, so a name like
  `site-a.import-engine.<domain>` gives `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`.
  Use hyphens too, an underscore is not allowed in a hostname.
- A **tunnel** and its token (below).
- Docker, k3d and kubectl on the machine, as for the local cluster.

## Steps

1. **Create the tunnel.** In the Cloudflare dashboard: Zero Trust, Networks,
   Tunnels, Create a tunnel, type *Cloudflared*, give it a name. Copy the token
   (the long string after `--token` in the install command). Do not run the
   command it shows; `deploy/tunnel.sh` does that part.
2. **Add the two public hostnames** to the tunnel:

   | Subdomain | Domain | Service |
   |---|---|---|
   | `site-a-import-engine` | your domain | `HTTP`, `web:80` |
   | `site-b-import-engine` | your domain | `HTTP`, `web:80` |

   Cloudflare ends TLS and keeps the host the visitor used, which is how the
   one web service tells the two sites apart.
3. **Start it.** Remove a local cluster first (`deploy/local.sh down`): the
   passwords of a cluster cannot be changed afterwards.

   ```bash
   CLOUDFLARE_TUNNEL_TOKEN=... TUNNEL_DOMAIN=example.com deploy/tunnel.sh up
   ```

   It builds the image, creates the cluster (without a port on this machine),
   makes random passwords, installs both sites, imports the catalog and starts
   `cloudflared`, then prints the two addresses and the passwords:
   `admin` (can change everything) and `demo` (can only look).
   `deploy/tunnel.sh passwords` shows them again. Other hostnames than these:
   set `SITE_A_HOST` and `SITE_B_HOST`, and for a cluster that already runs,
   `deploy/tunnel.sh hosts` applies them without installing again.
4. **Protect the front.** The login page of an administration interface is on
   the internet now. Put **Cloudflare Access** in front of both hostnames. A
   visitor needs no Cloudflare account: they fill in an email address, get a
   code by mail and are in, if the address is on your list. It is free for a
   small number of users.

   - Zero Trust, Access controls, Applications, **Add an application**,
     *Self-hosted*; add both hostnames to the one application.
   - A policy with action **Allow** and the rule *Emails* (the addresses that
     may come in) or *Emails ending in* (a whole organisation).
   - **Login methods must include One-time PIN**, in two places: the account
     (Settings, Authentication, Login methods, add *One-time PIN*) and the
     application (accept all methods, or tick it). If it is missing, visitors
     are asked to log in with a Cloudflare account, which they do not have.
   - Test in a private window, where you are not logged in to Cloudflare.

   Site B reads site A over the cluster's own network, not through Cloudflare,
   so the imports are not affected by Access.

## What a visitor with the demo account can do

The `demo` account (role *Import viewer*) can open the overview, the runs with
their items and events, the dead letter queue and the circuit breakers, and
cannot change anything. It cannot see the imports, connections, run sets and
settings screens: those need `administer import definitions`. To show those,
log in as `admin` yourself.

## Things to know

- **The machine has to be on.** If Docker or the machine restarts, start the
  cluster again with `k3d cluster start import-engine`; the tunnel reconnects
  by itself.
- **Everything is test data**, generated by the bootstrap job. The API key
  that site B reads site A with is random and only in the cluster.
- **Switching it off:** `deploy/tunnel.sh down` removes the cluster, with its
  database and files.
- **Image updates:** the image is built once on this machine
  (`import-engine:local`). After a code change, build, `k3d image import`, and
  restart the deployments.
